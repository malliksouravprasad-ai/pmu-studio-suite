# OSEPA PMU Tool Suite

## Mission

Build lightweight, output-driven PMU productivity applications that operate independently and generate actionable deliverables.

The objective is not to build a centralized platform.

The objective is to create a suite of reusable tools that help PMU teams collect, clean, validate, analyze, monitor, and report implementation data efficiently.

Applications should prioritize:

- Simplicity
- Speed
- Reusability
- Portability
- Minimal maintenance
- Fast deployment

Avoid enterprise-style platform engineering unless explicitly requested.

# Core Philosophy

Build tools.

Not platforms.

Build outputs.

Not infrastructure.

Build solutions.

Not ecosystems.

Every application should function independently.

Each application should:

Input → Process → Output

without requiring dependencies on other applications.

# Application Design Principles

## Rule 1

Every application must be standalone.

Examples:

District Ranking Tool

Input: district_data.xlsx

Output: district_ranking.xlsx district_ranking.pptx

No dependency on another application.

## Rule 2

Applications should be file-driven.

Preferred Inputs:

- CSV
- XLSX
- Google Sheet URL
- Google Form Response Sheet
- JSON (if required)

Preferred Outputs:

- XLSX
- CSV
- DOCX
- PPTX
- PDF

Applications should not require databases unless specifically requested.

## Rule 3

Avoid unnecessary complexity.

Do not introduce:

- Authentication
- User Management
- Role Management
- Multi-tenancy
- Complex APIs
- Enterprise Frameworks
- Microservices

unless explicitly required.

## Rule 4

Prefer templates over frameworks.

Create reusable:

- Excel Templates
- PowerPoint Templates
- Report Templates
- Dashboard Templates
- Survey Templates
- ATR Templates
- Meeting Templates

Templates are often more valuable than software abstractions in PMU environments.

## Rule 5

Automation should support existing workflows.

The purpose of automation is to reduce manual effort.

Automation should integrate naturally with:

- Excel
- Google Sheets
- Google Forms
- Word
- PowerPoint
- WhatsApp

Avoid changing how users already work unless there is a significant benefit.

# Serialization & Identification Standards

All outputs generated by any application must have a unique identifier.

Format:

PMU----

Examples:

PMU-2026-ADM-REPORT-00001

PMU-2026-FLN-SURVEY-00015

PMU-2026-ATR-00008

PMU-2026-MOM-00023

# Registry System

Maintain a lightweight registry.

Preferred Format:

registry.xlsx

or

registry.csv

Structure:

- App ID
- Artifact ID
- Date Generated
- Project
- Report Type
- Output File
- Status

Every application should update the registry when generating outputs.

The registry acts as the system-wide tracking mechanism.

No database required.

# Engineering Standards

Apply automatically.

- Clean code
- Modular structure
- Reusable components
- Input validation
- Error handling
- Logging
- Automated testing
- Self-verification

Every application should verify its own outputs before completion.

# Communication Rules

Focus discussions on:

- Inputs
- Outputs
- Reporting needs
- Monitoring needs
- Deliverables

Avoid discussing:

- Frameworks
- Libraries
- Databases
- APIs
- Infrastructure

unless specifically requested.

Always explain work in terms of what the PMU team will receive and use.

# Decision Framework

Before building any application ask:

- What file comes in?
- What processing is required?
- What file goes out?
- What manual effort does this remove?
- Can this tool be reused for another PMU assignment?

Optimize for practical usefulness over technical sophistication.

# Success Criteria

The tool suite is successful when:

- PMU teams spend less time manipulating data.
- Reporting becomes faster.
- Review preparation becomes easier.
- Deliverables are generated consistently.
- Applications can be reused across multiple assignments.
- Outputs are immediately usable in Excel, Word, PowerPoint, Google Sheets, and WhatsApp workflows.
